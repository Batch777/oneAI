# oneAI 设计评审与下一版 spec 建议

日期：2026-09-21。状态：历史讨论稿；以下目标设计尚未实现。

后续用户纠正：不需要 ehall，不是南京大学学生。下文相关内容来自最初通用示例，已从当前 SPEC-NEXT.md 的目标架构删除，不作为需求。

## 范围与已确认需求

- 评审本地 HEAD `aa7e800` 的 README、ARCHITECTURE、Python 核心、pi 扩展、Outlook connector、iOS 说明及测试。
- GitHub 连接器返回的默认分支提交列表只有初始提交 `df96c0c`；本地有 38 个提交。因此本地代码是本次实现评审依据，不能把线上默认分支当作当前完整实现。其他远程分支未全面核查。
- 用户确认：个人 Outlook / Hotmail；Mac 离线时也要持续收邮件、处理任务；原生手机 App 暂缓。
- 本轮先评审和讨论设计；未部署、购买服务器、接入真实邮箱或发送邮件。

## 结论

保留 Markdown、来源引用、FTS 检索和 pi 交互。优先补独立后台、可恢复任务、统一审批、规则加载和数据版本。暂不重写 TUI，也不把更长的模型上下文当作持久化方案。

目标架构：常在线的 oneAI 服务管理任务和授权；pi 作为可替换的推理执行器；手机网页或快捷指令直接访问服务；Mac/iCloud 作为资料同步适配器。Mac 离线后，仅依赖 Mac 文件或桌面浏览器的步骤进入等待，其余任务继续。

## 当前能力与需求差距

用户补充：部分实现是 legacy。根据当前 CLI 入口，按以下边界解释评审，不能把旧代码问题直接当作 pi 主路径故障：

| 分类 | 实际路径 | 本次评价方式 |
|---|---|---|
| 当前主路径 | `oneai → pi → extension/oneai → CLI search/read/draft → indexer/vault/agent` | 主路径问题优先处理 |
| 旧界面 | `oneai tui-legacy → Textual TUI` | 不建议继续投入；剪贴板测试失败不阻碍 pi 路线 |
| 独立/待退役入口 | `oneai ask → Python Runtime` | 仍可调用，但不代表 pi 的 agent loop；明确保留或弃用后再决定修复范围 |
| 未接入骨架 | Outlook connector、ledger | 评估接入前的设计缺陷，不描述成已上线邮件流程的故障 |

上述划分依据仓库调用关系，不推断用户目录中的私有扩展配置。Python Runtime 是否正式废弃尚待确认；即使完全删除它，主路径索引、任务恢复和跨工具上下文问题仍存在。

| 能力 | 仓库中实际具备 | 尚未具备 |
|---|---|---|
| 个人数据库 | Markdown、FTS5、中文 bigram 回退、文件行号引用、手动重建/单文件索引 | 自动变更/删除同步、版本化引用、PDF 解析和页码来源、语义召回评估 |
| Outlook | 个人账户 device-code 登录骨架、读取最近邮件预览、ledger 去重 | CLI 接入、delta 分页、正文/附件持久化、后台消费、草稿与发送闭环 |
| 手机 | vault 默认指向 iCloud Drive、Markdown 草稿文件 | 后台任务接收、进度投影、跨设备审批协议；ios/ 只有规划说明 |
| 能力组合 | pi 调 CLI 检索和独立起草 | 共享任务上下文、追问恢复、ehall 执行器、结果归档与完整端到端流程 |
| 成长 | 可手改资料、代码受 Git 管理、会话保存接口 | 纠正提炼、规则强制加载、规则版本/撤回、成功流程沉淀及跨会话回归测试 |

iCloud 手机文件联动按用户陈述视为现有可用能力；本轮未访问私人 vault，也未验证真实设备同步。

## 主要发现（按处理优先级）

### P1：无界面时审批默认放行

范围：Python Runtime 为独立/可能废弃入口；pi 扩展为当前入口，但其无 UI 行为涉及未来后台接入。普通 pi 交互模式已有弹窗拦截，不能声称当前所有审批都失效。

`oneai/runtime.py:333` 只有在 `confirm_cb` 存在且拒绝时才拦截；`confirm=True` 且没有回调会执行工具。`oneai ask` 未提供回调。`extension/oneai/index.ts:95` 在没有 UI 时直接跳过起草确认。

已用临时目录和假模型复现 Python 路径：带审批标志的合成工具在无审批回调时被执行。当前内置工具主要写草稿，不能据此说已经发生越权发邮件；但把这个机制沿用到无人值守发送会很危险。

修订 spec：审批是服务层的持久化授权记录，UI 只是展示入口。需要审批但没有有效批准时，返回 `waiting_approval`。读取、检索、任务范围内保存草稿可按明确策略自动执行；发送、提交等对外动作必须绑定具体内容版本的批准。不要让普通 bash 或通用网络工具绕过发送网关。

### P1：ledger 的“exactly once”承诺不成立

范围：未接入主路径的邮件处理骨架；属于接入前必须修正的设计承诺。

`connectors/outlook/connector.py:96` 在邮件完整保存或后续工作完成前就 claim；进程此后崩溃，再轮询会跳过。`oneai/ledger.py:62` 只改状态，不释放主键，且没有时间阈值；回退到 seen 后再次 claim 仍为 False，已复现。当前没有恢复 worker。

修订 spec：事件允许重复投递，任务按稳定键去重，步骤按状态和租约领取。外部副作用使用独立 outbox、操作 ID、提交记录和结果对账。发送超时且结果未知时进入 `uncertain`，先核验，不直接重发。数据库去重不能承诺远端邮件恰好发送一次。

### P1：邮件读取可能永久漏件

范围：Outlook connector 骨架；本轮未发现后台在真实轮询，以下是启用当前实现后会触发的漏件条件。

`connectors/outlook/connector.py:86` 实际只读最近 20 封，没有跟随 `@odata.nextLink`，也不是文件头所述的 delta query。两次轮询间超过 20 封、或离线积压时会漏掉更早邮件。只有 bodyPreview，无法可靠提取完整通知要求与附件。

修订 spec：按文件夹维护 delta cursor，逐页落地原始内容和任务后再推进游标。初次同步明确历史范围；过期游标可重建；覆盖更新和删除；处理限流、退避和重新授权。使用账户、文件夹范围和稳定邮件标识建立来源关系；Microsoft 的 ImmutableId 可避免同一邮箱内移动导致普通 ID 改变。[Graph delta](https://learn.microsoft.com/en-us/graph/delta-query-messages)、[ImmutableId](https://learn.microsoft.com/en-us/graph/outlook-immutable-id)。

### P1：现有 spec 缺少独立任务生命周期

仓库没有持续运行的 daemon、调度器或手机任务消费器，`watchdog` 只是依赖。`ios/README.md` 最后声称桌面 daemon 自动拾取，实际未实现。会话 JSONL 不是任务队列。

修订 spec：定义 `task_id`、触发来源、状态、步骤、证据、问题、回答、草稿版本、审批、执行回执和重试策略。关闭 pi 窗口不改变任务状态；服务重启可恢复等待和执行状态。Mac 不在线时不能让云端 worker 等待一个本地 UI 回调。

### P1：所谓 vault 读取没有路径边界

`oneai/runtime.py:137`、`oneai/cli.py` 的 read 分支和 `oneai/vault.py` 将调用者路径直接拼接。临时夹具证实 `vault_read('../outside.md')` 能读 vault 外文件；绝对路径和符号链接也应纳入检查。

修订 spec：工具先 resolve 并校验属于授权根目录，限制扩展名、大小和行范围。云端邮件内容是数据，不能因其中的“指令”扩大读取范围、改规则或授予发送权限。开发用 pi 与个人后台的工具白名单应隔离。

### P2：索引更新、引用稳定性与论文支持不足

索引只有显式 `index`/`index --file` 更新入口。已复现：编辑后搜索仍命中旧词、搜不到新词；删除后仍命中旧记录。rebuild 先删表再逐文件提交，失败时留下部分索引。行号无内容版本，原文修改后历史引用会漂移。标题被拼入 chunk 文本但引用范围只指正文，也要区分检索元数据与逐字证据。

修订 spec：文件扫描加内容 hash、增量 upsert/delete、周期性全量对账；重建完成后原子切换。引用保存 `document_id + source_version + locator + excerpt_hash`，保留可检验的原始版本。Markdown 用行号；论文用页码/段落定位。抽取文本和摘要可以重建，原论文及其版本不能丢失。

论文接入可评估 Docling，其官方项目提供 PDF 结构解析、表格和 OCR 能力；但需用用户真实论文验证公式、多栏、扫描件和中英文召回，不能假设转换成 Markdown 就等于精确页码溯源。[Docling](https://github.com/docling-project/docling)

### P2：对话与起草是分开的上下文

pi 的 `draft_create` 只向 Python 传 instruction；`oneai/agent.py:45` 重新检索并调用另一个 LLM。当前对话中刚给出的补充、纠正、选定证据不保证传入，pi 的模型设置也不控制这条起草管线。Python Runtime 又实现了一套 agent loop 和 draft_save。

修订 spec：使用持久化 TaskContext，包含明确约束、用户回答、来源版本、规则版本和产物；起草、问答、邮件、表单全部引用同一 task_id。选择一套主要推理入口，保留 Python 作为业务工具库，停止维护两套同等地位的 agent 引擎。

### P2：没有可验证的跨会话学习机制

Python 固定加载 identity.md，pi 只注入一般准则；没有通用规则加载器。把纠正放进普通笔记依赖偶然检索，不能保证新会话遵守。草稿目前排除索引是合理的，未来不能让模型产物未经确认自动变成个人事实。

修订 spec：规则有 ID、适用范围、来源、状态、版本和反例；关键规则每次构建相关任务上下文时强制加载。将“用户明确纠正”与“模型推测的偏好”分开；前者可按明确范围记录，后者先作为建议。成功流程经验证后沉淀为可编辑脚本/skill，支持撤回和回归测试。

### P2：文档混淆事实、规划和不可重建状态

README 同时称 pi 为主界面和兼容旧桥；ARCHITECTURE 仍把 pi 标为 legacy。`oneai` 实际只执行外部 pi，依赖用户目录中的扩展软链和配置，仓库没有自足的安装/依赖锁定流程，扩展还硬编码本机路径。

ARCHITECTURE 说 indexes 和 state 都能从 Markdown 重建；但授权、邮件游标、发送回执、任务执行状态不能靠当前笔记恢复。事件日志也只覆盖部分事件，不是完整可重放审计。文档应明确：原始资料和规则可阅读，业务状态是另一类必须备份的权威记录，索引才是可丢弃的派生物。

## 推荐的部署与职责

```text
个人 Outlook ── Graph delta ──┐
手机网页/快捷指令 ── API ─────┼─ oneAI 常在线后台 ── pi 推理 worker
Mac pi 客户端 ── API ────────┘         │
                                 任务/审批/操作记录
                                      │
                            云端授权资料副本 + 检索
                                      │
                         Mac 同步桥 ↔ iCloud Markdown
```

建议第一版用一台小型 Linux 主机运行 API、单 worker 和数据库，定时轮询 Graph；模型使用 API，云端不部署大模型。报价和地域先不锁定，部署前实测手机访问、Graph 和模型端点连通性，再按预算选择阿里云地域/规格。

服务器承担实际执行，单纯把 URL 转发到 Mac 不能满足 Mac 离线运行。默认资料同步边界必须明确：云端只拿用户选定的资料，显示同步版本；只在 Mac 上的文件，离线时标记不可用，不能假装拿到最新内容。

手机暂不开发原生 App，先用小型网页完成任务、追问、草稿和审批；快捷指令可把 iCloud 文件直接上传 API。现有 iCloud 路径依赖 Mac 本地挂载，仓库没有 Linux 同步实现，不能只改环境变量就宣称服务器拿到了 iCloud 文件。通过 Mac 的同步桥离线时暂停；需要即时处理的手机任务必须直接到云端。

避免云端和 iCloud 同时盲写同一文件。上传带 `document_id` 和 `base_version`，冲突保留两个版本，待合并后重索引；批准绑定内容 hash，编辑后批准失效。SQLite 文件不能放在 iCloud 中跨设备并发打开。

## pi 与其他实现的取舍

| 方案 | 对当前项目的价值 | 代价与建议 |
|---|---|---|
| pi SDK / RPC + oneAI 业务服务 | 复用现有模型接入、工具循环、session 与 compaction；后台可脱离 TUI | 首选渐进路线。SDK/RPC 不替代任务调度和持久审批；锁定版本，后台只暴露受控工具 |
| LangGraph | checkpoint、等待用户输入、恢复适合分支较多的跨工具流程 | 工作流变复杂时采用；可以保留 pi 作为一个推理步骤。恢复可能重跑节点，副作用仍需独立幂等设计 |
| Letta | 适合长期存在、带可编辑核心记忆的 agent | 值得做小规模对照验证；把状态中心迁入其体系会增加适配成本，仍需来源治理和发送策略 |
| Mem0 | 给现有 agent 增加记忆抽取/检索层 | 不是任务运行时，也不能把抽取结果直接当权威个人事实 |
| Graphiti | 人物、项目、事件关系及随时间变化的事实 | 等真实关联查询需求出现再引入图层；现阶段运维与建模成本偏高 |

上表适配判断为本评审建议，不是基准测试结果。来源：[pi SDK](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)、[LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)、[Letta](https://docs.letta.com/v1-sdk/concepts/stateful-agents)、[Mem0](https://github.com/mem0ai/mem0)、[Graphiti](https://github.com/getzep/graphiti)。

## 长上下文持久化：分层保存与按需恢复

1. 原始层：邮件、论文、笔记、用户消息与工具结果，带不可变来源版本。
2. 任务层：目标、约束、已完成步骤、未回答问题、产物与执行状态。每一步落盘。
3. 记忆层：用户确认的事实和适用规则，带生效时间、替代关系、撤回标记。
4. 当前上下文：本轮相关规则、任务摘要、检索证据和最近对话，按 token 预算组装。

可复用 pi 的 compaction，并通过扩展定制任务摘要；其官方文档提供 compaction 和分支摘要钩子。摘要只用于导航和恢复，不能覆盖原始来源、授权或关键日期。[pi compaction](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/compaction.md)

为你的例子建立规则 `notice.date_semantics`：报名截止时间与活动开始时间分别抽取，未提供的字段为 unknown，不用截止时间补开始时间；保存原文证据。测试用另一份通知启动全新会话，验证规则实际加载、日期字段正确且引用可回原文。这样才能衡量“成长”。

检索先保留 FTS；用一组真实中文问题和论文问题建立召回/引用基线，再试 embedding + 关键词混合召回和重排。衡量应包括来源是否正确、纠正是否生效、过期事实是否误用、压缩多轮后约束是否保留、每任务成本与延迟。

## Outlook 不需要先解决公网转发

当前个人账户方案可沿用 device-code 授权，首次用户在浏览器登录，服务端持久保存 token cache。这个流程不要求 OAuth 回调到 Mac 或购买 URL 转发服务。后台遇到需要重新登录时转入 `waiting_auth`，通知手机处理，不在 worker 中无限等待交互。[Microsoft device-code](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-device-code)

第一阶段用定时 delta 拉取，不需要公网 webhook；未来需要降低延迟再加入可公开访问的 HTTPS webhook，并处理验证、续订、重复通知和补拉。[Graph webhook](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks)

初期只申请读取所需权限；创建 Outlook 原生草稿再增加相应写入权限，发送时使用独立授权能力。凭据由服务读取并安全保存，不进入 Git、普通 vault 或模型上下文。授权和注册是否实际可用仍需真实账户验证。

## 第一条值得长期使用的完整流程

建议以“办事通知 → 待补材料 → 邮件回复”为首个验收流程，ehall 作为可插拔执行步骤：

1. Graph 持久化通知原文和附件，创建去重任务。
2. 读取日期规则，分别抽取截止/开始时间，保留证据及不确定项。
3. 检索个人资料和相关论文，输出已有材料/缺项清单。
4. 手机回答缺项；任务等待期间进程可重启，回答到达后继续。
5. 生成版本化邮件草稿和 ehall 字段映射。旧 spec 的“仅用户触发起草”要明确为任务授权策略：一次明确指派可覆盖本任务起草；自动收到任何邮件不默认拥有起草/发送授权。
6. 用户分别批准邮件和表单的具体版本；发送和提交分别记录结果，允许部分完成。
7. ehall 若需要校园网、验证码或 Mac 登录会话，单独标记等待，手机展示原因；邮件和其他独立任务继续。
8. 将实际执行回执、证据及产物归档。用户纠正进入规则版本，成功流程形成可编辑模板并用新通知回归。

ehall 的真实站点、登录与网络条件未提供，不能承诺现阶段能在云端自动提交。v1 可先验收邮件闭环，并清楚标注表单只是准备完成。

## 验收与实施顺序

| 阶段 | 交付 | 必须通过的验收 |
|---|---|---|
