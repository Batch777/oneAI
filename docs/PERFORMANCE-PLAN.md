# oneAI 交互延迟优化研究

2026-09-22；代码基线 `58b22f0`。状态：研究方案与分阶段实施记录；首屏聚合、分类预取和按行更新已实现，其余为建议。可复现基准在 `scripts/benchmark-ui-api.py`，只生成临时合成数据，不访问真实邮箱。

## 结论

目标是让分类切换和打开已读邮件尽可能不等待网络；数据库已经很快，优先减少串行请求、重复工作和无变化的重绘。继续保留现有轻量架构，按实际分层指标决定是否引入长期本地副本。

## 证据与限制

本地 10,000 条合成任务、25 次预热后的串行样本，SQLite 3.51.2，journal_mode=delete：

| 操作 | p50 | p95 |
|---|---:|---:|
| 当前过滤条件精确 count | 1.74ms | 1.86ms |
| 当前第一页 50 行查询 | 0.18ms | 0.20ms |
| OFFSET 5000 后取 50 行 | 1.32ms | 1.40ms |
| 已认证列表 API（TestClient） | 3.71ms | 3.89ms |
| 状态 API（TestClient） | 3.48ms | 3.60ms |

这是本机合成数据与 TestClient 开销，不含 TLS、香港网络 RTT、并发写锁、手机 JS/绘制；p95 仅描述这批小样本，不是生产 SLO。前轮线上第一页 SQL 为 2.13ms，也不是完整 API 延迟。未测得生产网络/渲染分层前，不宣称网络已经被证实为唯一瓶颈。

研究基线中的确定问题（前三项由下述首批优化处理）：

- `start()` 先 `/session`，之后请求 `/tasks`、`/status`、`/mail/alerts`，至少两轮依赖网络响应。
- 现有缓存只在访问分类后填充，未访问分类仍有冷请求。
- 每 15 秒轮询；列表未变化也 `replaceChildren()` 重建。打开详情时还会读取完整任务；分页后的列表也会被轮询重置回第一页。
- 列表 `count(*)` 只用于判断“加载更多”，目前 UI 不展示该筛选的精确总数。
- `auth.database()` 每次认证连接都 ensure_dirs、chmod 和 CREATE TABLE IF NOT EXISTS；这是不必要的初始化路径。不能据此断言每次都有实际 DDL 写入，需测量锁竞争。
- 验证邮件提醒每次读取最近 200 个 payload 并解析；导入时预计算提示可减少重复工作，但必须处理更新、删除、失效和规则升级。

## 推荐实施顺序

### P0：可测量与立即改善

1. **交互分层指标**：记录分类点击到首次正确列表绘制、cache hit/miss/stale、请求耗时、响应大小、DOM 更新耗时；结合已有 Server-Timing 区分网络与服务器。指标只含路由模板、耗时和数量，不上传邮件标题、搜索词或 ID。用真实 iPhone 测冷/热、弱网、两端同时修改及后台恢复，至少每场景 30 次并注明样本量。
2. **常用分类预取**：当前列表完成后按优先级预取其他分类第一页，空闲时最多一个请求，预算如最多 4 页/总计 256KiB，前台交互优先；搜索结果不盲目预取。桌面可用 focus/pointerenter 意图触发，手机不依赖 hover；节流与网络差时降级，退出或 generation 变化立即丢弃结果。预取只做本应用只读 GET，不触发 Graph 正文、外部图片、附件原件或生成操作。
3. **首屏 bootstrap**：一个已认证端点返回当前设备/CSRF、计数、当前分类第一页和轻量提醒，减少 `/session` 后的请求瀑布；认证后并行/同快照读取，不混入 Graph 网络调用。控制响应预算，非关键提醒允许独立加载，避免把慢子任务变成整个首屏阻塞。
4. **无变化不绘制**：同分类按 id/revision/status/显示日期/标题比较，内容相同保留 DOM、焦点、滚动和分页；变动时按 ID 更新。首次构建使用 fragment，一次插入。分页页面更新头部时去重并保持锚点，不能混拼不同快照的 offset 页面。

建议验收目标（待真机测量，并非已经达到）：缓存切换 p95 <100ms；点击反馈 <50ms；冷请求返回后到绘制 <50ms。完整冷启动时间单独报告网络条件，不承诺跨网固定 100ms。

### P1：让多端更新从“轮询”变成“变化通知”

- 引入持久 `change_seq` 与变更 outbox；所有任务、分类、归档、worker 写路径在同一事务记录变化。跨数据库不要伪造共同原子快照；采用各域 cursor 并明确聚合时的一致性。
- 每个客户端一个 SSE 通道推送失效通知（scope、变更域、cursor，不推邮件全文/验证码），写操作仍走现有 HTTP 命令与 revision 检查。需要刷新哪一页再按需拉取，而不是每次更新所有列表。
- 持久 cursor 支持断线补偿；日志超出保留范围时全量刷新。配置代理不缓冲、心跳和超时；移动端进入后台后连接可断，恢复前台检查 cursor。登录失效关闭连接并清缓存；每次事件验证 scope。服务端不可为每个 SSE 连接忙轮询 SQLite。
- 优先支持 HTTP/2；浏览器 HTTP/1 下 SSE 连接数有限，多标签要控制数量。SSE 是前台同步，不能替代系统锁屏推送。设置只发送失效信号且不压缩 SSE，避免 gzip/代理缓冲延迟。
- 若暂不做 SSE，先返回 snapshot revision；认证后的条件请求或轻量 revision 接口可以减少重复正文传输。304/ETag 本身仍要一次 RTT，不能取代本地缓存和预取。与 `no-store` 兼容性要明确；首版可只用显式内存 revision，不改成公共 HTTP 缓存。

### P1：后端成本与稳定性

- 给新客户端增加 `has_more` 模式，读取 51 行替代每页 count；旧 API 保持兼容。顶部精确统计单独更新，不把 count 成本放在每次列表切换中。
- 深分页改用 `(COALESCE(mail_received,updated), id)` 的不透明游标，绑定筛选/scope/version。日期或分类变化时仍要处理重复、缺失和锚点，cursor 不自动等于一致性快照。
- auth schema/权限初始化移到启动和迁移，仅保留逐请求读取与有效期检查；不通过长期认证缓存牺牲设备撤销即时性。
- 并发实测有读写互阻后再评估 WAL。启用前统一连接配置、backup API、checkpoint、磁盘上限和故障恢复；WAL 不取消单 writer 限制。云本地盘适用性与只读连接权限要验证，不能将 WAL 活数据库放 iCloud/网络盘同步。
- 提醒抽取结果与消息版本、规则版本绑定，收信时计算；查询到期时间索引，读取时再次判断有效期和删除状态。

### P2：进一步接近本地原生体验

长期方向可采用受控的本地只读投影：手机/Mac 存已授权的列表元数据，云端 delta 同步。绝大多数分类切换本地执行；正文独立按需加载，写操作离线排队但仍由服务端确认。

此方案增加本地敏感数据、同步冲突和删除传播成本，不默认开启。先仅保留内存缓存；如果用户明确需要重启后离线浏览，再设计系统保护的本地数据库、退出清除、scope 隔离、过期与撤销策略。远程撤销无法立即删除完全离线设备的数据，必须明确可用性与保留期。不会把 Outlook token 同步到手机。

## 不优先采用

- 为个人规模直接增加 Redis、微服务或更大云主机：尚无测量支持其收益。
- 共享 CDN 缓存认证 API/验证码；适合 CDN 的是无用户数据且带内容 hash 的静态资源，当前 no-cache 资源需先实现版本命名。
- 为 50 行列表先引入复杂虚拟滚动：先测真实 DOM 开销，长列表再考虑，兼顾屏幕阅读器和滚动锚点。
- 预加载全部邮件原文、附件或远程图片：浪费流量且违反现有图片确认行为。
- 用乐观 UI 提前标记“已核对/已发送”：可以显示“提交中”，最终状态和 revision 必须以服务器回执为准。
- 把 Chrome Speculation Rules 用于分类 AJAX 请求：它用于文档导航；本应用应使用显式、受预算约束的 API 预取。

## 主要参考

- [Google：stale-while-revalidate](https://web.dev/articles/stale-while-revalidate)：先返回缓存再更新的策略；oneAI 使用应用内私有缓存，不直接套公共响应缓存头。
- [Google：优化 INP](https://web.dev/articles/optimize-inp)：区分输入等待、事件处理与绘制，避免只优化网络。
- [WHATWG：Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html)：EventSource、重连与 Last-Event-ID 协议基础。
- [SQLite：查询规划](https://www.sqlite.org/queryplanner.html)、[WAL](https://www.sqlite.org/wal.html)：索引排序与读写并发的适用边界。
- [Chrome：预渲染与 Speculation Rules](https://developer.chrome.com/docs/web-platform/prerender-pages)：文档导航预加载与子资源预取的区别。


## 首批实现（2026-09-22）

- 新增已认证 `GET /api/bootstrap?q=&task_status=needs_review&mail_view=inbox`，返回 `session`、`tasks`、`status`。复用现有领域查询，旧接口保留；三个部分不是事务性的共同快照。邮件提醒独立加载，不在首屏等待 Graph 或正文解析。新前端遇到旧后端 404 时回退至旧接口。
- 当前列表完成后延迟 500ms，串行预取其他常用分类第一页。每次缓存 generation 最多 4 次尝试，累计响应达到 256KiB 后停止（软预算，最后一个响应可以超过阈值），每次 4 秒超时。搜索、隐藏页面、非任务页、支持网络提示的平台上的省流量/2G 跳过。前台请求优先；被取消的预取不会占用前台请求的去重入口。
- 按 ID 复用列表按钮，标题、状态、revision、日期、来源或分类展示变化才更新行内容；无变化保留节点。当前已加载列表刷新可一次取最多 500 条，旧客户端默认仍为 50 条；超过 500 条时刷新会收敛为前 500 条，可继续加载。此版本仍采用 offset，尚未提供跨分页原子快照与滚动锚点保证。
- 私有列表仅存页面内存，20 页/15 秒；操作与退出清缓存，API 保持 no-store。Service Worker shell v6，不缓存私有 API。
- 本地验证：167 项 Python core、19 项客户端测试通过。覆盖 bootstrap 认证与旧接口结果一致性、limit 边界、预取失效、前后台请求竞争、100 条刷新和不变行零子节点修改。

尚未完成真实 iPhone 30 次分层延迟测量，不将缓存机制或合成基准等同于生产 p95 达标。SSE、持久本地投影、认证初始化优化、has_more/cursor、提醒预计算保留为后续独立改动。
